# 초기 100 Cycle 기반 배터리 수명 예측
## Day 1 — 어떤 초기 신호가 배터리의 미래 수명을 설명하는가?

---

## 0. Executive Summary

이 프로젝트의 목적은 배터리를 끝까지 시험하지 않고 **초기 100 cycle만으로 Cycle Life(처음부터 수명 종료까지의 총 충·방전 횟수)**를 예측하는 것이다. Batch 1·2·3의 원본 139개 셀을 점검했고, 수명 정답이 있는 129개 셀을 같은 기준으로 비교했다. Day 1에서는 수명 분포, 초기 방전용량, 전압별 용량 변화, 충전 조건, 센서 신호 중 무엇이 미래 수명을 설명하는지 질문했다. 분석 결과 Batch마다 수명 분포가 크게 달라 외부 데이터에서의 일반화를 별도로 확인해야 했다. 초기 방전용량 자체는 배치 안에서 수명과의 관계가 약했지만, cycle 10에서 100까지 전압별 방전곡선이 변한 정도인 **ΔQ(V)**는 세 Batch에서 비교적 일관된 강한 관계를 보였다. 따라서 Day 2에서는 연속적인 수명 숫자를 예측하는 **Regression**을 수행하고, ΔQ(V)를 Core Feature(핵심 입력 변수)로 두되 중복 변수의 영향을 줄이는 Ridge·ElasticNet과 비선형 모델을 비교한다. Feature군을 한꺼번에 넣지 않고 단계적으로 추가해 동일한 검증 조건에서 **평균 절대 백분율 오차(MAPE)**가 실제로 개선되는지 확인한다.

> **가장 중요한 발견**  
> 초기 Capacity 자체 → Cycle Life와의 관계가 배치 안에서 약함  
> 초기 ΔQ(V) → 세 Batch에서 상대적으로 일관된 강한 관계  
> **따라서 → ΔQ(V)를 Day 2 Core Feature군으로 선정**

---

## 1. 문제 정의 — 왜 배터리 수명을 미리 예측해야 하는가?

### 1.1 이번 프로젝트가 풀려는 문제

배터리의 실제 수명을 알려면 수백에서 수천 번 충·방전을 반복해 수명 종료 시점까지 기다려야 한다. **Cycle**은 충전과 방전을 한 번 수행한 단위이며, **Cycle Life**는 배터리가 처음 사용된 시점부터 **SOH(State of Health, 초기 설계용량 대비 현재 건강도) 80%**에 해당하는 EOL(End of Life, 수명 종료)까지 버틴 총 cycle 수다.

이번 프로젝트는 전체 열화 과정을 기다리는 대신, 관측 초반인 **100 cycle 이내의 정보로 최종 Cycle Life를 예측**한다. 예측이 가능해지면 ESS 배터리의 점검·교체 시점을 더 일찍 계획하고 장기간 수명시험에 필요한 시간과 비용을 줄일 수 있다.

### 1.2 Input과 Target

**Input — 초기 100 cycle**

- **QD(방전용량):** 한 번 방전할 때 실제로 꺼낼 수 있는 전하량
- **Q(V):** 전압이 변할 때 방전 가능한 용량이 어떻게 달라지는지 나타내는 곡선
- **IR(내부저항):** 배터리 내부에서 전류 흐름을 방해하는 정도
- **온도:** cycle 중 평균·최고·최저 온도
- **충전시간:** 한 cycle의 충전에 걸린 시간
- **Charging Policy:** 충전 속도와 속도를 전환하는 시점을 정한 실험 조건

↓

**Regression Model — 여러 초기 신호로 연속적인 수명 숫자를 예측**

↓

**Target — `cycle_life`**

`cycle_life`는 “100 cycle 이후 남은 수명”이 아니라 **처음부터 EOL까지의 총 cycle 수**다. Day 2의 한 행, 즉 하나의 독립 학습 Sample은 cycle 한 개가 아니라 **Battery Cell 한 개**다.

### 1.3 Day 1에서 답하려는 다섯 가지 질문

1. **Target은 Batch마다 어떻게 다른가?** 먼저 모델이 맞혀야 할 수명 범위와 분포가 데이터 묶음마다 같은지 확인한다.
2. **수명 차이가 초기 Capacity에서 이미 보이는가?** 가장 직관적인 신호인 방전용량만으로 장수명과 단수명을 구분할 수 있는지 살펴본다.
3. **Capacity의 절대값보다 ΔQ(V)가 더 유용한가?** 초기 100 cycle 안에서 전압별 방전곡선의 미세한 변화가 수명 차이를 포착하는지 확인한다.
4. **충전 조건이 수명 차이를 설명하는가?** 빠른 충전이 짧은 수명으로 이어진다는 단순한 규칙이 데이터에서도 반복되는지 검증한다.
5. **어떤 신호를 Day 2 후보로 남길 것인가?** 관계의 크기뿐 아니라 Batch 간 일관성과 Feature 간 중복까지 고려해 후보군을 좁힌다.

## 2. 데이터 이해 — 무엇을 분석했는가?

### 2.1 Dataset

| Dataset | 전체 Cell | Target 보유 Cell | Target 결측 Cell |
|---|---:|---:|---:|
| Batch 1 | 46 | 46 | 0 |
| Batch 2 | 47 | 39 | 8 |
| Batch 3 | 46 | 44 | 2 |
| **합계** | **139** | **129** | **10** |

여기서 **Batch**는 서로 다른 시기와 실험 조건에서 수집된 Cell 묶음이다. Batch 1은 Day 2 모델 개발에 사용하고, Batch 2는 모델과 Feature 선택이 끝난 뒤 외부 테스트에 사용한다. Batch 3은 추가적인 일반화 분석용이다. Day 1에서 Batch 2·3의 정답은 데이터 차이를 이해하는 데만 사용하며 모델 튜닝에는 사용하지 않는다.

### 2.2 Cell과 Cycle의 데이터 구조

데이터는 **Battery Cell → Cycle → Cycle 안의 측정값** 순서로 구성된다. 한 Cell에는 시간, 전압, 전류, 온도, 충·방전 용량과 같은 cycle별 기록이 반복해서 쌓인다.

EDA에서는 이 반복 측정을 펼쳐 열화 과정을 살펴보지만, Day 2에서는 초기 100 cycle을 요약해 **Cell 한 개당 Feature 행 한 개**를 만든다. 따라서 기록된 cycle 수가 많더라도 독립적인 학습 Sample 수는 129개 수준이라는 점이 모델 복잡도를 정할 때 중요하다.

### 2.3 데이터 품질에서 먼저 확인한 것

- Batch 1의 모든 Cell은 첫 summary cycle에 실측값이 아닌 0 채움값(placeholder)이 있어 실제 초기 통계는 cycle 2부터 계산했다.
- Batch 2의 8개 Cell과 Batch 3의 2개 Cell은 `cycle_life`가 결측이다.
- Batch 2의 7개 Cell은 초기 IR이 미가용이고, 3개 Cell은 초기 Tmin에 비정상 값이 있다.
- 첫 cycle placeholder와 일부 물리 범위 밖 QD 값이 있어 유효 범위 밖 측정은 초기 Feature 계산에서 제외했다.
- 결측 `cycle_life`를 관측된 기록 길이로 임의 대체하지 않았다.

> **데이터 처리 원칙**  
> 이후 분석에서는 실제 측정값과 결측 표현을 구분하고, 이상값이 있다는 이유만으로 원본 Cell을 임의 삭제하지 않았다. Target이 필요한 분석에서는 정답이 있는 129개 Cell만 사용했다.

## 3. EDA — 초기 수명 신호를 좁혀가는 다섯 가지 질문

### 3.1 Q1. 세 Batch의 수명 분포는 같지 않았다

**왜 확인했는가?**  
모델이 예측해야 할 Target의 범위가 Batch마다 같다고 가정할 수 있는지 확인하기 위해서다. 학습 데이터와 외부 데이터의 수명 분포가 다르면, 학습 데이터에서 좋은 모델이 다른 Batch에서도 그대로 잘 작동한다고 보장할 수 없다.

**어떻게 확인했는가?**  
Target이 있는 Cell만 사용해 Batch별 histogram과 누적분포를 비교하고, 중앙값과 단·장수명 비율을 계산했다. Kruskal-Wallis 검정은 세 Batch의 순위 분포 차이가 우연으로 보기 어려운지 확인하는 보조 근거로만 사용했다.

| Batch | Target 수 | Cycle Life 중앙값 | 분포의 특징 |
|---|---:|---:|---|
| Batch 1 | 46 | **858.5** | 500~1,000 cycle에 주로 분포 |
| Batch 2 | 39 | **472.0** | 500 cycle 미만이 **71.8%** |
| Batch 3 | 44 | **1,005.5** | 1,000 cycle 초과가 **52.3%** |

![Batch별 Cycle Life 분포와 누적분포](../figures/day1/01_수명_분포.png)

> **이 그림에서 볼 것**  
> Batch 2는 짧은 수명 쪽에 집중되어 있고 Batch 3은 긴 수명 쪽으로 이동해 있다. 세 Batch가 같은 Target 분포에서 나온 것처럼 보이지 않는다.

**무엇을 발견했는가?**  
세 Batch의 수명 중앙값은 **472.0~1,005.5 cycle**로 크게 달랐다. 분포 차이는 통계적으로도 확인됐다(Kruskal-Wallis H=53.925, p=1.95×10⁻¹²).

**어떻게 해석할 수 있는가?**  
실험 시기, 충전 프로토콜, Cell 구조 등의 차이가 함께 반영됐을 가능성이 있으므로 특정 요인의 인과효과로 단정할 수 없다. 일부 장수명 특이 Cell에서 `newstructure` 정책이 관찰됐지만 Batch 효과와 구조 효과가 섞여 있어 이 정책만을 원인으로 볼 수 없다.

> **Day 2 결정**  
> Batch 1 내부 성능만으로 일반화를 판단하지 않는다. Batch 1에서 Feature와 모델을 선택한 뒤 Batch 2를 별도의 External Test로 평가하고, Batch 3에서 추가적인 분포 이동을 확인한다.

### 3.2 Q2. 수명 차이는 초기 Capacity만으로 잘 보이지 않았다

**왜 확인했는가?**  
배터리가 노화하면 QD가 감소하므로, 가장 단순한 초기 Capacity 수준이나 변화만으로 미래 수명을 구분할 수 있는지 확인했다.

**어떻게 확인했는가?**  
초기 cycle 2~100의 QD 평균과 기울기를 비교하고, 설명을 위해 전체 수명 동안의 대표 열화곡선을 살펴봤다. **Knee Point**는 완만하던 용량 감소가 빠르게 가속되기 시작하는 시점이다.

![수명 그룹별 대표 방전용량 열화곡선](../figures/day1/04_대표_셀_열화.png)

> **이 그림에서 볼 것**  
> 초기 구간에서는 장수명·중간수명·단수명 Cell의 Capacity가 모두 비슷하게 유지되고 일부는 소폭 증가한다. 뚜렷한 차이는 수명이 상당히 진행된 뒤 급격한 열화가 시작될 때 나타난다.

**무엇을 발견했는가?**  
초기 QD 평균과 Cycle Life의 Batch별 **Spearman 상관(두 값의 순위가 함께 움직이는 정도를 -1~1로 나타낸 값)**은 Batch 1 **0.242**, Batch 2 **0.117**, Batch 3 **0.162**로 모두 약했다. 초기 QD 기울기는 Batch 1에서 0.479였지만 Batch 2에서는 -0.271로 방향이 달라, 초기 Capacity trend만으로 일반화하기 어려웠다. 반면 전체 곡선에서 구한 knee cycle과 Cycle Life의 상관은 **ρ=0.934**로 매우 강했다.

**어떻게 해석할 수 있는가?**  
수명과 연결되는 열화 신호 자체는 존재하지만, 눈에 띄는 Capacity 감소와 knee는 대체로 미래 구간에서 나타난다. 전체 곡선을 본 뒤 계산한 knee는 예측 시점에 알 수 없는 정보이므로 강한 상관만 보고 모델 입력으로 사용하면 Data Leakage가 발생한다.

> **Day 2 결정**  
> 초기 Capacity는 비교 기준과 보조 Feature로 남기되, knee와 전체 수명곡선 파생값은 입력에서 제외한다. 다음 질문에서는 100 cycle 안에서 관찰할 수 있는 더 미세한 변화인 ΔQ(V)를 확인한다.

### 3.3 Q3. ΔQ(V)에서 가장 뚜렷한 초기 수명 신호가 나타났다

**왜 확인했는가?**  
Capacity의 절대값은 초기 구간에서 큰 차이가 없었다. 따라서 “얼마나 큰가”보다 cycle 10에서 100까지 **전압별 방전곡선의 형태가 얼마나 변했는가**를 확인했다.

**ΔQ(V)는 무엇인가?**  
Cycle 10과 cycle 100에서 같은 전압을 비교했을 때 방전 가능한 용량이 얼마나 달라졌는지를 나타낸다.

> **ΔQ(V) = Q₁₀₀(V) - Q₁₀(V)**

**어떻게 확인했는가?**  
실제 cycle 번호 10과 100의 `Qdlin`을 공통 전압축에서 뺀 뒤, Batch별 수명 상·하위 25%의 ΔQ(V) 곡선을 비교했다. 이어 곡선 변화의 크기를 요약하는 로그분산과 Cycle Life의 **상관관계**, 즉 두 값이 함께 증가하거나 감소하는 경향을 확인했다.

![장수명·단수명 그룹의 ΔQ(V) 곡선](../figures/day1/06_deltaQ_곡선.png)

> **이 그림에서 볼 것**  
> 단수명 그룹은 장수명 그룹보다 cycle 10→100 사이의 방전곡선 변화 폭이 크다. 이 차이는 특정 Batch에만 나타나지 않고 세 Batch에서 같은 방향으로 관찰된다.

![ΔQ(V) 로그분산과 Cycle Life의 관계](../figures/day1/07_deltaQ_상관.png)

> **이 그림에서 볼 것**  
> ΔQ(V) 로그분산이 커질수록 Cycle Life가 짧아지는 방향이 세 Batch에서 반복된다. 전체 상관 하나가 아니라 Batch별 방향이 유지된다는 점이 핵심이다.

| Batch | ΔQ 로그분산과 Cycle Life의 Spearman ρ | 해석 |
|---|---:|---|
| Batch 1 | **-0.871** | 강한 음의 관계 |
| Batch 2 | **-0.709** | 같은 방향의 강한 관계 |
| Batch 3 | **-0.797** | 같은 방향의 강한 관계 |

**무엇을 발견했는가?**  
초기 방전곡선 변화가 클수록 최종 수명이 짧아지는 방향이 세 Batch에서 비교적 일관되게 나타났다. ΔQ 로그분산은 전체 데이터에서도 ρ=-0.892였고, 수명 상·하위 그룹의 곡선 차이 역시 세 Batch에서 같은 방향이었다.

**어떻게 해석할 수 있는가?**  
ΔQ(V)는 Capacity의 작은 변화를 전압 구간별 형태로 드러내기 때문에, 초기 QD 평균보다 열화 차이에 민감한 신호로 해석할 수 있다. 다만 이는 강한 **연관성**이며, ΔQ(V)가 짧은 수명을 직접 일으킨다는 인과관계는 아니다.

> **Day 2 결정**  
> ΔQ(V) 통계량을 Core Feature군으로 선정한다. 다만 분산·표준편차·로그분산처럼 거의 같은 정보를 담는 변수를 모두 넣지 않고, Batch 1 CV(Cross-Validation, 학습 데이터를 여러 번 나눠 성능을 확인하는 방법)와 규제를 통해 대표 변수를 선택한다.

### 3.4 Q4. 빠른 충전 하나만으로 수명을 설명할 수 없었다

**왜 확인했는가?**  
충전 속도는 열화에 영향을 줄 가능성이 있으므로, Charging Policy가 수명 차이를 추가로 설명하는지 확인했다. **C-rate**는 배터리 용량 대비 충전 전류의 크기로, 값이 클수록 더 빠르게 충전한다는 뜻이다.

**어떻게 확인했는가?**  
정책 문자열을 1단계 C-rate, 전환 SOC, 2단계 C-rate로 나눴다. 1단계 C-rate와 Cycle Life의 산점도를 Batch별로 비교하고, 정책별 평균 수명에는 표본 수와 bootstrap 95% 신뢰구간(표본을 반복 재추출해 계산한 불확실성 범위)을 함께 표시했다.

![충전 조건과 Cycle Life의 관계](../figures/day1/08_충전_정책.png)

> **이 그림에서 볼 것**  
> 같은 C-rate에서도 수명이 넓게 퍼지고, 정책별 평균의 불확실성도 크다. “빠르게 충전할수록 반드시 짧게 산다”는 하나의 직선 규칙으로 설명하기 어렵다.

| 범위 | 1단계 C-rate와 Cycle Life의 Spearman ρ | 판단 |
|---|---:|---|
| 전체 | **-0.027** | 사실상 관계 없음 |
| Batch 1 | **-0.483** | 음의 관계 |
| Batch 2 | **0.055** | 방향이 뒤집히며 매우 약함 |
| Batch 3 | **-0.229** | 음의 방향이지만 약함 |

**무엇을 발견했는가?**  
Batch 1에서는 높은 1단계 C-rate와 짧은 수명이 함께 나타났지만 Batch 2·3에서 같은 크기의 관계가 반복되지 않았다. 일부 Charging Policy는 Cell 수가 1~2개여서 평균 수명만으로 정책 효과를 판단하기도 어렵다.

**어떻게 해석할 수 있는가?**  
충전 조건과 수명의 관계에는 Batch, Cell 구조, 온도 등 다른 요인이 함께 섞여 있을 수 있다. 따라서 관찰된 차이를 충전 속도의 인과효과로 단정하지 않는다.

> **Day 2 결정**  
> Charging Policy 전체 문자열을 주요 Feature로 고정하지 않는다. C-rate와 switch SOC 같은 연속형 정보를 후보로 만들고, ΔQ 중심 모델에 추가했을 때 동일한 CV에서 MAPE가 실제로 줄어드는지 검증한다.

### 3.5 Q5. 중요한 것은 높은 상관보다 일관성과 중복 제거였다

**왜 확인했는가?**  
상관이 큰 Feature를 많이 넣는다고 예측이 자동으로 좋아지는 것은 아니다. Batch마다 관계 방향이 유지되는지, 그리고 여러 Feature가 사실상 같은 정보를 반복하는지 확인해야 한다.

**어떻게 확인했는가?**  
초기 100 cycle에서 Capacity, IR, Temperature, Charge Time, Charging Condition, ΔQ Feature군을 만들었다. 선형 관계를 보는 Pearson과 순위 기반 관계를 보는 Spearman을 함께 확인하고, Batch별 방향성과 Feature끼리의 상관을 비교했다.

![초기 Feature 간 상관관계](../figures/day1/10_다중공선성.png)

> **이 그림에서 볼 것**  
> ΔQ 분산·표준편차·로그분산 등은 서로 거의 같은 정보를 표현한다. 이런 변수를 동시에 많이 넣으면 독립 Sample이 적은 데이터에서 계수가 불안정해지는 **다중공선성** 문제가 생길 수 있다.

| Feature군 | Cycle Life와의 일관성 | 중복·품질 이슈 | Day 2 판단 |
|---|---|---|---|
| **ΔQ(V)** | 세 Batch에서 강하고 같은 방향 | 파생변수끼리 중복이 매우 큼 | **Core, 대표 변수 선택** |
| Capacity | 평균 관계는 약하고 slope 방향이 다름 | 수준·변화량 간 중복 가능 | Baseline·보조 후보 |
| IR | 관계가 약하고 Batch별 방향이 다름 | Batch 2 일부 초기값 미가용 | Incremental 후보 |
| Temperature | 대부분 약하거나 방향이 다름 | Tavg·Tmax 등 서로 중복 | 대표 변수만 검증 |
| Charge Time | Batch 1·2에서 관계 방향이 반대 | C-rate의 대리 정보 가능 | 추가 가치 확인 |
| Charging Condition | 전체 관계가 약하고 불일치 | 정책별 표본이 작음 | 마지막 단계에서 검증 |

**무엇을 발견했는가?**  
세 Batch에서 가장 강하고 방향이 일관된 Feature군은 ΔQ(V)였다. 반면 Capacity trend, IR, Temperature, Charge Time, Charging Condition은 일부 Batch에서 관계가 보이더라도 다른 Batch에서 약해지거나 방향이 바뀌었다.

**어떻게 해석할 수 있는가?**  
전체 데이터를 합친 상관은 Batch 간 평균 차이 때문에 커질 수 있으므로, 전체 순위보다 Batch별 일관성을 우선해야 한다. 또한 ΔQ Feature 여러 개를 동시에 투입하면 “정보가 많아지는 것”이 아니라 같은 정보를 반복해 넣는 결과가 될 수 있다.

> **Day 2 결정**  
> 높은 상관 Feature를 많이 넣지 않는다. ΔQ를 중심으로 서로 다른 정보를 주는 Feature군을 하나씩 추가하고, Ridge·ElasticNet 규제와 Feature Ablation(Feature군을 단계적으로 추가·제거해 성능 기여를 확인하는 실험)으로 실제 개선 여부를 판단한다.

## 5. Feature Engineering Strategy

Day 1에서 Feature를 최종 확정한 것은 아니다. 과적합과 중복을 피하기 위해 **Day 2에서 검증할 후보군과 투입 순서**를 정했다.

### 5.1 Core Feature — ΔQ(V)

`delta_q_log10_var`를 대표 후보로 둔다. cycle 10과 100만 사용해 누수 위험이 낮고, Batch 1·2·3에서 Cycle Life와 같은 방향의 강한 관계를 보였다. `delta_q_min`과 면적·분위수 계열은 같은 곡선에서 나온 후보이므로 모두 고정 투입하지 않고 CV에서 대표성을 비교한다.

### 5.2 Baseline Feature — 초기 Capacity

초기 QD 평균과 slope를 가장 단순한 기준 Feature로 사용한다. 단독 설명력은 제한적이지만, ΔQ가 Capacity baseline보다 실제로 얼마나 개선하는지 보여주는 비교 기준이 된다.

### 5.3 Incremental Feature — Sensor와 Charging

IR, Temperature, Charge Time, Capacity trend, C-rate, switch SOC는 ΔQ에 없는 추가 정보를 줄 가능성이 있다. 그러나 Batch별 관계가 불안정하므로 하나의 큰 Feature 묶음으로 바로 넣지 않고 군별로 추가한다.

### 5.4 제외 Feature — 미래정보

Knee point, EOL 도달 시점, `cycle_life` 자체와 그 파생값, cycle 100 이후의 측정값은 예측 시점에 알 수 없다. 상관이 높아도 모두 입력에서 제외한다.

| Feature군 | 역할 | Day 1 근거 | Day 2 사용 방식 |
|---|---|---|---|
| ΔQ(V) | Core | 세 Batch에서 강하고 일관된 관계 | 대표 Feature 선택 |
| Capacity | Baseline | 단독 관계가 제한적 | F0 기준선 |
| Sensor | Incremental | 일부 Batch에서만 관계 | 군별로 하나씩 추가 |
| Charging | Incremental | 관계가 비일관적 | 추가 MAPE 개선 확인 |
| Knee·EOL | 제외 | 미래정보가 필요함 | 사용 금지 |

## 6. 왜 Regression인가?

Classification은 Cell을 “장수명/단수명”처럼 정해진 등급으로 나눈다. 반면 Regression은 **총 몇 cycle까지 사용할 수 있는지 숫자로 예측**한다.

ESS 유지보수와 교체 시점을 정량적으로 판단하려면 “긴가, 짧은가”보다 “몇 cycle인가”가 더 직접적인 정보다. 따라서 Target을 연속형 `cycle_life`로 두는 Regression을 선택한다.

주 평가지표는 **MAPE(Mean Absolute Percentage Error)**다. MAPE는 실제 수명과 예측 수명의 차이를 실제값 대비 백분율로 나타내므로, 예를 들어 MAPE 10%는 평균적으로 실제 수명의 약 10% 정도를 벗어났다는 뜻이다.

원논문이 보고한 테스트 오차 **9.1%**는 성능을 가늠하는 benchmark로 사용한다. 다만 현재의 전처리, Feature 구성, split 조건이 논문과 완전히 동일하다고 확인한 것이 아니므로 “9.1%를 동일 조건에서 재현했다”고 표현하지 않는다.

## 7. Day 2 Modeling Strategy

### 7.1 데이터 특성이 말해주는 것

- 독립 학습 Sample은 cycle 수가 아니라 **Cell 수**이므로 Batch 1은 46개로 작다.
- ΔQ 파생변수와 온도 변수처럼 서로 비슷한 Feature가 많다.
- ΔQ와 수명의 관계는 강하지만 완전히 선형이라고 보장할 수 없다.
- Sensor와 Charging Feature가 ΔQ에 추가 정보를 주는지는 아직 확실하지 않다.

이 조건에서는 복잡한 모델 하나를 바로 선택하기보다, 단순한 기준부터 규제 선형모델과 비선형 모델을 같은 검증 조건에서 비교하는 것이 적절하다.

### 7.2 비교할 모델과 선택 이유

| 모델 | 선택 이유 |
|---|---|
| Baseline 중앙값 | ML 모델이 단순 예측보다 실제 가치를 만드는지 확인 |
| Linear Regression | 가장 단순한 선형 관계와 계수 방향 확인 |
| Ridge | 작은 데이터와 다중공선성에 대응하도록 계수를 안정화 |
| ElasticNet | 중복 Feature의 계수를 축소하고 일부를 선택할 가능성 |
| Gradient Boosting 또는 LightGBM | ΔQ·Sensor·Charging 사이의 비선형 관계와 interaction 검증 |

Deep Learning은 우선 후보에서 제외한다. cycle 기록은 많아도 독립 Sample은 Cell 수십 개 수준인 tabular dataset이므로, 큰 신경망의 복잡도를 뒷받침할 학습 표본이 부족하고 과적합 위험이 크다.

### 7.3 Feature Ablation — 무엇이 실제로 성능을 높였는가?

| 단계 | 사용 Feature | 확인할 질문 |
|---|---|---|
| F0 | Capacity baseline | 가장 단순한 초기 용량만으로 어느 정도 예측되는가? |
| F1 | ΔQ | 변화 형태가 baseline보다 MAPE를 줄이는가? |
| F2 | ΔQ + Capacity trend | 용량 변화 속도가 추가 정보를 주는가? |
| F3 | F2 + Sensor | IR·Temperature·Charge Time이 개선을 만드는가? |
| F4 | F3 + Charging Condition | C-rate·switch SOC가 마지막 추가 가치를 주는가? |

처음부터 모든 Feature를 넣지 않고, 새로운 Feature군이 **동일한 CV split에서 평균 MAPE와 fold 편차를 실제로 개선하는지** 확인한다. 이 Ablation은 Feature 선정 이유를 상관계수보다 직접적으로 보여준다.

## 8. Validation Strategy — 외부 일반화와 누수를 분리한다

**Batch 1 모델 개발**  
→ **Batch 1 CV:** Feature군과 모델 후보 비교  
→ **Batch 1 고정 Hold-out:** 선택된 조합 점검  
→ **Batch 2 External Test:** 모든 선택이 끝난 뒤 한 번 평가  
→ **Batch 3:** 추가 Generalization 분석

Batch 1 안에서 먼저 Hold-out을 고정하고, 나머지 개발 데이터의 K-fold CV로 F0~F4와 모델을 비교한다. 선택이 끝난 후보만 Hold-out에서 점검하고, Batch 2의 정답은 이 과정에 되먹임하지 않는다. Batch 3은 Batch 2와도 다른 분포에서 결과가 얼마나 유지되는지 보는 추가 분석으로 사용한다.

> **Data Leakage 방지**
>
> - 모델 입력은 cycle 100까지의 정보만 사용한다.
> - Knee, EOL 등 미래정보를 사용하지 않는다.
> - Cell 한 개를 Sample 한 개로 유지하고 동일 Cell을 Train과 Validation 양쪽에 넣지 않는다.
> - Imputer, scaler, encoder는 전체 데이터가 아니라 각 Train fold에서만 fit한다.
> - Batch 2·3의 정답으로 Feature나 hyperparameter를 반복 선택하지 않는다.

최종 선택은 CV 평균 MAPE만 보지 않는다. fold 간 편차, Hold-out과의 Gap, Feature 수, 계수·중요도의 설명 가능성을 함께 확인해 작은 표본에서 더 안정적인 조합을 선택한다.

## 9. 한계와 다음 단계

- **Sample 수가 작다.** 복잡한 모델의 작은 성능 차이는 split에 따라 달라질 수 있으므로 CV 평균과 편차를 함께 보고 단순한 모델을 우선한다.
- **정책별 Sample은 더 작다.** Charging Policy별 평균 차이를 인과효과로 해석하지 않고, 연속형 충전조건의 추가 예측가치만 검증한다.
- **Target 결측 Cell이 10개다.** 이들이 중도절단된 장수명 Cell이라면 관측된 수명 분포가 치우쳤을 수 있으므로 기록 길이로 임의 보정하지 않는다.
- **Batch별 분포 차이가 크다.** Batch 1 CV 성능과 Batch 2·3 성능을 분리해 보고하고 외부 성능 저하 자체를 중요한 결과로 해석한다.
- **실험실 Cell 데이터다.** 실제 ESS의 온도 구배, Cell 불균형, 운영 부하를 모두 대표하지 않으므로 현장 수명으로 직접 일반화하지 않는다.

Day 2에서는 F0~F4 Ablation과 모델 비교를 먼저 완료한 뒤, 선택된 단일 pipeline을 Batch 2에서 평가한다. 핵심 성공 기준은 Feature 수를 늘리는 것이 아니라 **ΔQ 중심의 작은 Feature 집합이 외부 Batch에서도 안정적인 MAPE를 만드는지** 확인하는 것이다.
